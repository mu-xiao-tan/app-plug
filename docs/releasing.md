# App Plug 发版手册

`main` 和 PR 跑相同的六个原生构建作业，并下载本次运行的产物检验整套包，但不会发布。自动发布仅由首次推送 `vMAJOR.MINOR.PATCH` 正式标签触发，也不会自动创建标签。发布标签必须受保护、位于 `main` 历史上，且与实际构建出的 CLI 版本相同。

## 一次性保护设置

开关默认关闭。仓库管理员先确认：

1. `main` 受保护：变更通过 PR 合入，要求 `App Plug CI required` 成功。
2. 生效的仓库标签 Ruleset 覆盖 `v*.*.*`：仅授权发布者可创建，禁止未授权更新和删除。不要用重打或移动标签处理失败。
3. 建立环境 `github-release`。部署策略只允许 `v*.*.*` 类型为 Tag 的规则，不配置分支规则。指定与标签推送人不同的必需审核人，勾选禁止自审，关闭管理员绕过。
4. 核实仓库和组织都没有名为 `APP_PLUG_RELEASE_ENABLED` 的 Actions **secret**。上述保护已独立复核、启用获批后，只在 `github-release` 环境中创建该 secret，值为精确的 `true`。仓库变量或环境变量不适用。

工作流在只读作业检查标签受保护、环境的审批人、禁止自审及标签部署策略。查询失败，或审批字段缺失、类型不符、审核名单无有效身份时，检查失败，不进入发布审批。管理员绕过设置、Ruleset 的适用范围和推送人与审核人是否确实独立仍须人工核对。未通过时不要推送正式标签。

## 发版与验收

1. 版本在 `src/server/server.go` 的 `Version`。待版本随 PR 合入 `main`，指定提交的主分支 CI 六目标全绿后，由已获授权的标签推送人在复核 SHA 后创建并显式推送该版本标签。
2. 检查这次标签运行的提交 SHA、六个原生目标和 `App Plug CI required`。独立审核人仅在获批发版且证据齐备后批准 `github-release`。
3. 发布作业只下载同一标签运行的原生产物，重新计算并核对六个包的 SHA-256，并确认当前标签仍指向同一提交。Release 发布六个包和一个聚合 `SHA256SUMS`，发布说明带提交 SHA 和 Actions 运行链接。
4. 从公开 Release 下载所有资产，对照聚合清单校验。保留发布、运行和审批证据。签名、公证、系统服务安装和实际部署另做验收。

如果校验或审批失败，不手传文件来冒充自动发布成功，不移动标签，也不覆盖已发布的 Release。先检查标签运行是否留下了草稿，再按仓库发版审批处理；排除运行环境或审批配置故障后，可以按授权重跑原标签运行，源码缺陷则修正并发布新的版本。紧急暂停时按审批移除环境开关，取消仍在等待的发布运行。
